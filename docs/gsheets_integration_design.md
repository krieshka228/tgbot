## 1. Требования заказчика (как получены)

1. Заказы из Telegram-группы автоматически заносятся в Google-таблицу.
2. Номенклатура сохраняется: закуп проставляется вручную один раз, дальше подставляется автоматически.
3. Второй лист — такая же таблица для розницы (ручное оформление заказов в магазине).
4. Клиенты разделяются; в колонках «Итого» подводятся итоговые суммы закупа и продажи.

## 2. Анализ текущего кода бота

Примечание: `bot/script.py`, упомянутый в задаче, в репозитории больше не
существует (debug-скрипт с захардкоженным токеном, удалён в коммите `09086ee`).
Анализ выполнен по актуальному коду: `bot/db.py`, `bot/main.py`, `bot/utils.py`,

### 2.1 Где сохраняются заказы

Два пути создания заказа, оба сходятся в одни таблицы БД:

| Путь | Код | Механика |
|---|---|---|
| Каталог в личке бота | `bot/handlers/checkout.py` | корзина (черновик `Order`) → «Оформить» → статус `pending` → клиент шлёт чек → `paid` → админ подтверждает → `confirmed` |
| Комментарий в группе обсуждения канала | `bot/handlers/posts.py` (`handle_comment`) + `bot/handlers/fsm_inputs.py` (`porder_confirm`, ~строка 898) | покупатель пишет количество в комментарии к посту → `PendingOrder` → бот пишет в личку с кнопкой `porder:confirm:...` → после подтверждения создаётся `Order` + `OrderItem` |

Статусы заказа (`OrderStatus` в `bot/db.py`, строка 51):
`draft → pending → paid → confirmed → exported`, плюс `cancelled`.

### 2.2 Какие данные о заказе уже собираются

- **Order**: `id`, `user_id`, `status`, `delivery_address`, `contact_phone`,
  `full_name`, `bonus_used`, `receipt_file_id`, `total_amount`,
  `delivery_method`, `created_at`, `updated_at`.
- **OrderItem** (состав): `product_id`, `quantity`, `price_at_order` —
  цена фиксируется на момент заказа.
- **User** (клиент): telegram `id`, `username`, `full_name`, `phone`,
  `address`, бонусные балансы (TG/MAX), `platform`, `consented`, `created_at`.
- **Product** (номенклатура): `id`, `post_id`, `name`, `price` (розничная),
  `stock`, `article`, `category`, `description`, `in_stock`, `is_active`.

**Вывод:** всё необходимое для п.1, п.2, п.4 требований уже есть в БД.
Не хватает только **закупочной цены** — в `Product` её нет (есть только
розничная `price`). Это единственное новое поле, которое потребуется.

## 3. Структура таблицы

### 3.1 Лист «Опт» (заказы из Telegram — заполняется ботом автоматически)

| Колонка | Источник | Пример |
|---|---|---|
| A: Дата | `Order.created_at` | 2026-09-11 |
| B: ID заказа | `Order.id` | 154 |
| C: Клиент | `User.full_name` / `username` | Иван (@ivan) |
| D: Телефон | `Order.contact_phone` | +7… |
| E: Товар (артикул) | `Product.article` + `name` | AB-123 Кроссовки X |
| F: Кол-во | `OrderItem.quantity` | 2 |
| G: Цена закупа (авто) | `VLOOKUP` по листу «Справочник» | 1500 |
| H: Сумма закупа (формула) | `=F*G` | 3000 |
| I: Цена продажи (авто) | `VLOOKUP` / `price_at_order` | 2500 |
| J: Сумма продажи (формула) | `=F*I` | 5000 |
| K: Статус | `Order.status` | confirmed |
| L: ID позиции (служебная) | `OrderItem.id` | 812 |

Одна строка = одна позиция заказа (не один заказ) — так работают формулы
«Итого» и сводные таблицы. Колонка L нужна боту для идемпотентности
(защита от дублей, см. п.7).

**Итоги:** под таблицей или отдельным блоком —
`=SUMIF(C:C; клиент; H:H)` (закуп) и `=SUMIF(C:C; клиент; J:J)` (продажа);
лучше — сводная таблица (Pivot table) по клиенту: закуп, продажа, маржа.

### 3.2 Лист «Розница» (заполняется вручную продавцом в магазине)

Та же структура колонок A–K, но:
- строки вносит человек (дата, товар из выпадающего списка, кол-во, клиент «Розничный» или имя);
- G и I подтягиваются `VLOOKUP` из «Справочника» автоматически;
- H и J — формулы;
- бот этот лист **только читает** (для итогов), не пишет.

### 3.3 Лист «Справочник» (номенклатура)

| Колонка | Заполнение |
|---|---|
| Артикул | бот синхронизирует из `Product.article` |
| Название | бот синхронизирует из `Product.name` |
| Цена закупа | **вручную, один раз** (требование п.2) |
| Цена продажи (розница) | бот подставляет из `Product.price`, закупщик может поправить |
| Категория | бот из `Product.category` |
| В наличии | бот из `Product.in_stock` |

Бот периодически (job-queue, например раз в час или по команде админа)
обновляет строки товаров: новые добавляет, существующие сверяет по артикулу,
**колонку «Цена закупа» никогда не перезаписывает** — она заполняется вручную.
Это и реализует «закуп проставляется один раз, потом подставляется автоматически».

### 3.4 Разделение клиентов (п.4)

Вариант A (рекомендуется): колонка «Клиент» на листах «Опт»/«Розница» +
сводная таблица с итогами закуп/продажа/маржа по каждому клиенту.
Вариант B: отдельный лист «Клиенты», куда бот пишет список
(`User.full_name`, `username`, телефон, дата регистрации) — используется как
источник для валидации имён и как справочник, а итоги всё равно сводной.
Итоговые суммы считаются **формулами в Google Sheets**, а не на стороне бота —
продавец может добавить ручные строки, и итоги пересчитаются сами.

## 4. Архитектура интеграции

### 4.1 Аутентификация

- Google Cloud Console → проект → включить **Google Sheets API** (и Drive API).
- Создать **Service Account**, скачать `credentials.json`.
- Владельцы таблицы выдают сервисному аккаунту доступ «Редактор»
  (по email вида `...@...iam.gserviceaccount.com`).
- `credentials.json` кладётся на сервер рядом с `.env`, в `.gitignore`;
  в `.env` добавляются `GOOGLE_SHEET_ID` и `GOOGLE_CREDENTIALS_PATH`.

### 4.2 Библиотека

**Рекомендация: `gspread`** (+ `google-auth` для сервисного аккаунта).
- `gspread` — самый простой API (`sh.append_row`, `sh.update`), идеально
  подходит для «дописать строку / обновить диапазон».
- `pygsheets` — альтернатива, менее активна.
- `google-api-python-client` — низкоуровневый, больше кода, нужен только
  для сложных сценариев (batch-запросы больших объёмов).

### 4.3 Новый модуль бота

`bot/gsheets.py`:
- `GoogleSheetsClient` — обёртка над gspread: `append_order_rows(order)`,
  `sync_nomenclature()`, логирование ошибок, retry с exponential backoff.
- **Очередь отправки**: заказы пишутся в таблицу не синхронно в хендлере,
  а через таблицу-очередь в БД (`gsheets_outbox`: `order_item_id`, `sent_at`,
  `error`) + job-queue джоба, которая разбирает очередь раз в N минут.
  Причины: Google API может быть недоступен/медленный; нельзя блокировать
  оформление заказа; нужна защита от дублей при рестартах.
- Точки вызова: `checkout.py` (после `confirmed`) и `fsm_inputs.py`
  `porder_confirm` (после создания заказа) — добавляют заказ в outbox.

### 4.4 Расчёт итогов

Формулы в Google Sheets (SUMIF / сводная таблица). Бот ничего не суммирует.

## 5. Как это выглядит для пользователя

- **Покупатель (Telegram):** ничего не меняется — заказ как раньше через
  каталог или комментарий; подтверждение оплаты админом как раньше.
- **Админ/закупщик (таблица):** после подтверждения заказа (`confirmed`)
  в листе «Опт» в течение нескольких минут появляются строки заказа с
  автоподставленным закупом; в «Справочнике» новые товары появляются сами,
  закупщик проставляет цену закупа один раз.
- **Продавец в магазине:** открывает лист «Розница», выбирает товар из
  выпадающего списка (data validation по «Справочнику»), вводит количество —
  цены и суммы подставляются сами.
- **Руководитель:** сводная таблица — по каждому клиенту закуп, продажа, маржа.

## 6. Оценка реализуемости 4 пунктов

| Пункт | Сложность | Комментарий |
|---|---|---|
| 1. Заказы → таблица | Низкая | Все данные уже в БД; gspread `append_row` + outbox |
| 2. Номенклатура с ручным закупом | Низкая-средняя | Синк товаров из БД + правило «не перезаписывать цену закупа» |
| 3. Лист «Розница» для ручного ввода | Низкая (для бота) | Бот почти не участвует: шаблон листа, data validation, формулы настраиваются один раз |
| 4. Разделение клиентов + «Итого» | Средняя | Идентификация клиента — по `full_name`/`username`/телефону; возможны тёзки и смена имени → нужен стабильный ключ (telegram id в служебной колонке) |

## 7. Риски и вопросы заказчику

1. **Доступ к таблице:** кто владеет, кто редактор; сервисному аккаунту
   нужен доступ — кто его выдаст.
2. **Двусторонняя синхронизация:** нужна ли (изменения в таблице → бот,
   например правка цены закупа ботом)? Рекомендуется НЕТ на первом этапе
   (только бот → таблица), иначе резко растёт сложность.
3. **Дубли заказов:** решаются служебной колонкой `OrderItem.id` + проверкой
   перед вставкой / unique constraint в outbox.
4. **Логирование закупа:** нужно ли фиксировать, кто и когда вносил цену
   закупа (в Google Sheets это история изменений; отдельный лог — доп. работа).
5. **Формат итогов:** за период (месяц), по клиенту, общие? От этого зависит
   вид сводной таблицы.
6. **Стабильная идентификация клиента:** имя в Telegram можно сменить —
   подтвердить, что ключом является telegram id / телефон.
7. **Лимиты Google Sheets API:** ~60 запросов/мин на проект — при текущих
   объёмах не проблема, outbox-джоба их сглаживает.
8. **Закупочная цена в БД бота:** добавить поле `purchase_price` в `Product`
   (или хранить закуп только в таблице — тогда бот его не видит; рекомен-
   дуется первое).
9. **Розничные заказы:** должны ли они попадать в статистику бота, или
   живут только в таблице? (по текущему ТЗ — только в таблице).
10. **Курс/валюты, НДС** — уточнить, нужны ли отдельные колонки.

## 8. План внедрения по этапам

**Этап 0 — подготовка (0.5 дня):** Google Cloud проект, Sheets API,
сервисный аккаунт, `credentials.json`, доступ к таблице, `gspread` в
requirements, настройки в `.env`/`config.py`.

**Этап 1 — минимальная версия (1–2 дня):** `bot/gsheets.py` + outbox-таблица
+ job-джоба; при `confirmed` строки заказа уезжают в лист «Опт»; защита от
дублей; логирование ошибок. *Результат: п.1 требований закрыт.*

**Этап 2 — номенклатура (1 день):** лист «Справочник», синк товаров
(артикул/название/розница/категория), колонка «Цена закупа» — только ручная,
бот не трогает; `purchase_price` в БД (опционально); VLOOKUP-формулы в «Опт».
*Результат: п.2 закрыт.*

**Этап 3 — розница (0.5–1 день):** шаблон листа «Розница», data validation
товаров из «Справочника», формулы автоподстановки цен и сумм.
*Результат: п.3 закрыт.*

**Этап 4 — клиенты и итоги (1 день):** служебный ключ клиента (tg id),
лист/блок «Клиенты», сводная таблица закуп/продажа/маржа по клиентам
и периодам. *Результат: п.4 закрыт.*

**Этап 5 — стабилизация:** мониторинг ошибок отправки, уведомление админа
в Telegram при сбое синхронизации, регламент ручных правок таблицы.

Итого: ~4–5 рабочих дней на все этапы.

## 12. Лимиты Google (ответ на встречный вопрос «какие лимиты?»)

- **Google Sheets API:** ~60 запросов в минуту на проект. Бот отправляет
  заказ одним batch-запросом, т.е. даже 100 заказов в день — это единицы
  запросов в минуту. Outbox-очередь дополнительно сглаживает пики.
  На текущих и ожидаемых объёмах лимит недостижим.
- **Размер таблицы:** 10 млн ячеек на таблицу. При ~12 колонках на позицию
  это сотни тысяч строк — годы работы без приближения к лимиту. При
  необходимости старые месяцы архивируются на отдельный лист/файл.
